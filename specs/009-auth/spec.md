# Feature Specification: 로그인

**Feature Branch**: `009-auth` | **Created**: 2026-11-02 | **Status**: Implemented
**Input**: 3단계 순서(STT·번역 → 문장 다듬기 → **로그인** → 학습 짝 메시지 수신·알림), 헌법 v2.0.0 (백엔드 = Supabase), [supabase-foundation.md](./supabase-foundation.md)
**서브도메인**: 계정 (Generic). **흐름**: draft.md §4 전 단계에 "누구의 것인지"를 주는 상류다. 이 기능만으로 바뀌는 §4 단계는 없다.

## User Scenarios & Testing

### User Story 1 - 이메일로 가입하고 로그인하기 (Priority: P1)

학습자가 이메일·비밀번호·표시 이름으로 가입하고, 다음부터 이메일과 비밀번호로 로그인한다.
**Why this priority**: 학습 짝 메시지 수신(다음 기능)은 누가 보냈고 누가 받는지가 있어야 한다.
**Independent Test**: 상단 계정 버튼 → 가입 → (확인 메일이 꺼져 있으면) 바로 로그인 상태, 상단에 표시 이름.

**Acceptance Scenarios**:
1. **Given** 로그아웃 상태, **When** 상단 "로그인"을 누른다, **Then** 계정 화면에 로그인/가입 전환과 입력 폼이 보인다.
2. **Given** 가입 모드, **When** 표시 이름·이메일·비밀번호를 올바르게 넣고 제출, **Then** 프로젝트 설정에 따라 바로 로그인되거나 "확인 메일을 보냈어요"가 보인다.
3. **Given** 확인 메일의 링크, **When** 누른다, **Then** 앱으로 돌아와 계정 화면에 "이메일 확인을 마쳤어요"와 로그인 상태가 보인다. 링크가 만료됐으면 그 사실을 알린다.
4. **Given** 로그인 모드, **When** 맞는 이메일·비밀번호로 제출, **Then** 로그인 상태가 되고 새로고침·화면 이동 후에도 유지된다.

### User Story 2 - 로그아웃하기 (Priority: P2)

**Why this priority**: 공용 기기에서 계정을 끝낼 수 있어야 한다.
**Independent Test**: 로그인 상태에서 로그아웃 → 확인 → 로그인 폼, 상단 "로그인".

**Acceptance Scenarios**:
1. **Given** 로그인 상태, **When** 로그아웃을 누른다, **Then** "이 기기에서 로그아웃할까요?"와 기록이 남는다는 안내가 보인다.
2. **Given** 확인 단계, **When** 취소 또는 Escape, **Then** 아무 일도 없고 포커스가 로그아웃 버튼으로 돌아온다.
3. **Given** 확인 단계, **When** 로그아웃, **Then** 로그아웃 상태가 되고 이 기기의 학습방·표현·카드는 그대로다.

### User Story 3 - 로그인 없이도 그대로 쓰기 (Priority: P1)

**Why this priority**: 지금까지의 Core 흐름은 계정 없이 검증됐다. 로그인이 기본 행동을 막으면 안 된다 (원칙 V).
**Independent Test**: 키가 없는 빌드와 로그아웃 상태 모두에서 녹음·학습방·카드·복습이 그대로 동작한다.

**Acceptance Scenarios**:
1. **Given** Supabase 설정이 없는 환경, **When** 상단 "계정"을 누른다, **Then** "이 환경에서는 로그인을 쓸 수 없어요"가 보이고 입력 폼은 없다.
2. **Given** 로그아웃 상태, **When** 앱의 다른 기능을 쓴다, **Then** 로그인을 요구하는 화면·리디렉션이 없다.

### Edge Cases

- 이미 가입된 이메일: 확인 메일이 켜져 있으면 Supabase 는 오류 대신 identities 가 빈 사용자를 돌려준다. 두 경우 모두 "이미 가입된 이메일"로 알린다.
- 확인 전 로그인: "아직 이메일 확인 전이에요"로 알린다.
- 리디렉션 주소가 Supabase 허용 목록에 없으면 Site URL(`/?code=`)로 돌아온다. 브라우저 클라이언트가 교환하고 결과를 같은 방식으로 알린다.
- Supabase 에 닿지 못할 때 페이지 요청의 세션 갱신 실패는 로그아웃 상태와 같게 다루고 페이지는 열린다.
- 표시 이름은 앞뒤 공백을 빼고 1~20자다. 표시 이름이 없는 계정은 이메일 앞부분을 보여 준다.

## Requirements

### Functional Requirements

- **FR-001**: 이메일·비밀번호(6~72자)·표시 이름(1~20자)으로 가입한다. 표시 이름은 `user_metadata.display_name` 에 둔다.
- **FR-002**: 이메일·비밀번호로 로그인한다. 로그인 상태는 새로고침·화면 이동 후에도 유지된다.
- **FR-003**: 확인 메일 켜짐/꺼짐 두 설정을 모두 처리하고, 확인 링크(`/auth/confirm`)의 성공·실패를 계정 화면에서 알린다.
- **FR-004**: 로그아웃은 확인 단계를 거치고, 이 기기의 세션만 끝낸다.
- **FR-005**: 상단 바에 계정 진입점을 둔다. 로그아웃 상태는 "로그인", 로그인 상태는 표시 이름, 확인 중·설정 없음은 "계정"이다.
- **FR-006**: 로그인해도 학습방·표현·카드는 이 기기에만 저장된다는 사실을 계정 화면에 보인다 (원칙 II). 계정으로 옮기는 기능은 다음 기능이다.
- **FR-007**: 로그인은 선택이다. 키가 없거나 Supabase 에 닿지 못해도 다른 기능은 그대로 동작하고 빌드는 통과한다.
- **FR-008**: 상태 — 입력 오류, 처리 중(중복 제출 방지), 잘못된 자격 증명, 이미 가입됨, 확인 전, 약한 비밀번호, 쓸 수 없는 이메일, 가입 막힘, 요청 빈도 초과, 시간 초과(15초), 네트워크 실패. 문구는 사용자 언어이며 Supabase 원문을 노출하지 않는다.
- **FR-009**: 비밀번호는 브라우저 저장소·로그에 남기지 않는다. secret/service_role 키를 쓰지 않는다.
- **FR-010**: 서버 측 사용자 확인은 `getClaims()`(또는 `getUser()`)로 하고 `getSession()` 값을 권한 판단에 쓰지 않는다.
- **FR-011**: 모든 컨트롤은 키보드로 조작된다. 모드 전환은 `aria-pressed`, 처리·결과는 `role="status"`/`role="alert"`, 폼·버튼이 사라지면 포커스를 제목으로 옮긴다.

### Key Entities

- 계정 상태: 확인 중 · 설정 없음 · 로그아웃 · 로그인(사용자 id, 이메일, 표시 이름).
- 확인 안내: 확인 링크에서 돌아온 결과(완료 · 실패). 한 번 보여 주고 주소에서 지운다.

## Success Criteria

### Measurable Outcomes

- **SC-001**: 확인 메일이 꺼진 프로젝트에서 가입부터 로그인 상태까지 화면 하나, 제출 한 번이다.
- **SC-002**: 실패 상태 각각이 사용자 문구로 보이고 입력(비밀번호 제외)을 잃지 않는다.
- **SC-003**: 처리 중 제출을 반복해도 인증 요청은 1회다.
- **SC-004**: 키 없는 빌드에서 계정 화면은 "쓸 수 없음"을 보이고 페이지 오류는 0이다.
- **SC-005**: 로그아웃 전후로 이 기기의 학습방·표현·카드 수가 같다.

## Assumptions

- Supabase Auth 만 쓴다. DB 테이블·마이그레이션·RLS 정책은 첫 테이블을 만드는 기능(기록을 계정으로 옮기기)에서 둔다.
- 소셜 로그인, 비밀번호 재설정, 이메일 변경, 계정 삭제, 사용자 단위 AI 요청 빈도 제한은 범위 밖이다.
- 확인 메일 발송은 Supabase 기본 메일 서버를 쓴다. 기본 서버는 시간당 발송 수와 받는 주소가 제한될 수 있다.

## Clarifications

### Session 2026-11-02

- 로그인을 강제하는가? → 아니다. 선택이다.
- 기존 기기 기록을 계정으로 옮기는가? → 이번에는 옮기지 않고 사실을 안내한다. 옮기는 방식은 다음 기능에서 정한다.
- 로그인 방식? → 이메일 + 비밀번호. 표시 이름은 가입 시 받는다.
- 로그인 화면 위치? → 별도 경로가 아니라 셸 안의 계정 화면. 근거는 research.md R1.
