# Phase 0 Research: 스크립트에서 표현 선택·저장

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-09

Technical Context의 미확정 항목과, Constitution 원칙 IV(최소 의존성)·원칙 III(접근성)이
요구하는 검토 결과를 정리한다.

---

## R-001: 고른 범위를 읽는 방법

**Decision**: `window.getSelection()`으로 읽는다. 선택이 스크립트 요소 안에서 일어났는지
`transcriptEl.contains(range.commonAncestorContainer)`로 확인하고, 밖이면 무시한다.
선택 확정 시점은 `document`의 `selectionchange`와 `pointerup`·`keyup`을 함께 듣는다.

**Rationale**: `Selection`은 마우스 드래그·터치 롱프레스·키보드(`Shift`+방향키)로 만든
선택을 **모두 같은 방식으로** 노출한다. 입력 수단별로 코드를 나누지 않아도 되고, 그래서
FR-028(키보드로 고르기)이 추가 UI 없이 따라온다(R-002 참조).

`commonAncestorContainer` 검사가 필요한 이유는 사용자가 화면의 다른 텍스트(상대 이름,
번역, 안내 문구)를 선택했을 때 저장 수단이 뜨면 안 되기 때문이다. FR-006이 요구하는
"스크립트가 열려 있을 때만"도 이 검사로 자연히 만족된다 — 스크립트가 닫히면 요소 자체가
없다.

`selectionchange`만 듣지 않고 `pointerup`·`keyup`을 함께 듣는 이유는 브라우저 사이
`selectionchange`의 발생 시점과 빈도가 다르기 때문이다. 두 경로 모두 같은 읽기 함수를
부르게 하면 어느 쪽이 먼저 와도 결과가 같다.

**Alternatives considered**:
- 스크립트 글자를 하나씩 `<span>`으로 쪼개고 탭으로 범위를 고르게 하기 — 선택 UI를 완전히
  통제할 수 있지만 문자 수만큼 DOM 노드가 늘고, 브라우저 기본 선택 동작과 충돌하며,
  키보드 경로를 따로 만들어야 한다.
- 형태소 분석기(kuromoji 등)로 단어 경계를 잘라 토큰 단위로 고르기 — 원칙 IV 위반이고,
  결정 D-1("표현은 단어·구·문장을 모두 포함")과 어긋난다. 사전에 없는 표현을 고를 수
  없게 된다.

## R-002: 키보드로 범위 고르기 (FR-028)

**Decision**: 스크립트 요소에 `tabIndex={0}`를 주는 것으로 끝낸다. 별도의 키보드 전용
선택 UI를 만들지 않는다.

**Rationale**: 포커스 가능한 텍스트 요소 안에서는 `Shift`+방향키로 캐럿 선택이 되고,
그 선택이 `getSelection()`에 똑같이 나타난다. 즉 R-001의 읽기 경로 하나가 마우스·터치·
키보드 세 입력을 모두 처리한다. 원칙 III의 MUST를 코드 한 줄로 만족한다.

`tabIndex={0}`을 준 요소에는 스크린리더가 읽을 수 있도록 무엇을 하는 영역인지 알리는
설명이 필요하다. `aria-label`로 "스크립트. 배우고 싶은 부분을 골라 표현으로 저장할 수
있어요"를 붙인다.

**Alternatives considered**:
- "문장 전체 저장" 버튼을 키보드 대안으로 두기 — 접근 가능해지지만 키보드 사용자만 단어를
  고를 수 없게 되어 결정 D-1의 취지에 어긋난다. 접근성을 기능 축소로 바꾸는 것은 원칙
  III의 의도가 아니다.
- `contentEditable`로 만들어 캐럿을 확보하기 — 선택은 쉬워지지만 사용자가 스크립트를
  실수로 고칠 수 있고, 모바일에서 키보드가 올라온다.

## R-003: 저장소 선택

**Decision**: `localStorage`에 단일 키(`talklog.expressions`)로 JSON 배열을 저장한다.
읽기·쓰기·삭제를 모두 `try`/`catch`로 감싸고, 실패하면 `unavailable` 상태로 전이한다.

**Rationale**: 저장할 것은 짧은 문자열 몇 개짜리 레코드 수십~수백 개다. `localStorage`의
5MB 한도 안에서 충분하고 동기 API라 상태 관리가 단순하다. `IndexedDB`는 비동기 트랜잭션
모델을 들여야 하는데 얻는 것이 없다 — 원칙 IV가 요구하는 정당화를 넘기지 못한다.

`try`/`catch`가 필수인 이유는 **접근 자체가 예외를 던지는 환경이 있다**는 것이다.
브라우저 설정에서 사이트 데이터를 차단하면 `localStorage`에 접근하는 순간 `SecurityError`가
나고, 저장소가 가득 차면 쓰기에서 `QuotaExceededError`가 난다. 사생활 보호 모드에서도
할당량이 작거나 0일 수 있다. 이 경로가 FR-015("저장 실패를 성공처럼 표시하지 말 것")의
근거다.

**Alternatives considered**:
- `IndexedDB` — 위 이유로 기각. 표현 개수가 수천 개를 넘고 검색이 필요해지면 재검토한다.
- `sessionStorage` — 새로고침은 견디지만 탭을 닫으면 사라져 FR-014의 의도(복습이 의미를
  가지려면 남아야 한다)를 만족하지 못한다.
- 표현마다 별도 키로 저장 — 개별 쓰기가 가벼워지지만 목록을 읽을 때 키를 순회해야 하고
  순서 보장을 직접 해야 한다. 단일 배열이 더 단순하다.

## R-004: 서버 렌더링과 "아직 읽지 않음" 상태

**Decision**: `useExpressions`의 상태를 `loading` / `ready` / `unavailable` 3가지로 둔다.
저장소 읽기는 `useEffect` 안에서만 하고, 첫 렌더는 항상 `loading`이다. 빈 상태 안내는
`ready`이고 표현이 0개일 때만 보여준다.

**Rationale**: `"use client"` 컴포넌트도 서버에서 한 번 렌더링되므로 렌더 중에
`localStorage`를 읽으면 서버와 클라이언트의 결과가 달라 hydration 이 어긋난다. 001의
R-002에서 `MediaRecorder` 판정을 `useEffect`로 옮긴 것과 같은 문제다.

여기서 그치지 않고 상태를 3가지로 나눈 이유는 **`loading`과 "저장한 것이 없음"을 같은
화면으로 처리하면 표현이 있는 사용자에게도 빈 상태 안내가 한 순간 보인다**는 것이다.
FR-019가 요구하는 빈 상태는 "정말 없을 때"의 안내이고, 있는데 잘못 보이면 사용자는 저장이
사라졌다고 오해한다. 원칙 V가 요구하는 상태 구분에 해당한다.

**Alternatives considered**:
- 상태 2가지(`ready` / `unavailable`)에 `expressions`를 `null`로 두어 구분 — 동작은 같지만
  `null`과 `[]`의 의미 차이를 읽는 쪽이 매번 기억해야 한다. 이름 있는 상태가 낫다.
- 첫 렌더에서 동기로 읽고 `suppressHydrationWarning` 사용 — 경고만 숨기고 불일치는 남는다.

## R-005: 중복 판정 방법 (FR-021)

**Decision**: 표현 본문을 `trim()` 한 뒤 `normalize("NFC")` 로 정규화해 문자열이 같은지
비교한다. 예문이 달라도 같은 표현으로 본다(spec.md Assumptions의 결정).

**Rationale**: 앞뒤 공백은 끌어서 고를 때 거의 항상 섞여 들어오므로 `trim()` 이 없으면
`過ごした` 와 `過ごした ` 가 다른 표현이 된다. `normalize("NFC")` 는 일본어 입력기에서
결합 문자로 들어온 문자열(예: 반각 가나 + 결합 탁점)을 같은 표현으로 묶어준다. 둘 다
표준 API 호출 한 번이라 원칙 IV에 걸리지 않는다.

전각·반각 통일이나 활용형 원형 복원(`過ごした` → `過ごす`)은 하지 않는다. 활용형 복원은
형태소 분석기가 필요하고, 학습자에게는 실제로 들은 형태를 저장하는 것이 더 유용하다 —
결정 D-1의 근거("다음에 내가 쓸 수 있는가")와 같은 논리다.

**Alternatives considered**:
- 정규화 없이 그대로 비교 — 공백 하나로 중복이 생겨 FR-021이 사실상 무력해진다.
- 표현 + 예문 조합으로 판정 — 같은 표현을 여러 대화에서 만날 때마다 카드가 늘어난다.
  복습 대상이 중복되는 것은 FR-021이 막으려던 문제 그 자체다.

## R-006: 저장 수단을 어디에 띄우는가

**Decision**: 선택 위에 떠 있는 버튼이 아니라, 스크립트 블록 바로 아래에 붙는 고정 영역에
띄운다. 선택이 유효해지면 그 영역이 나타나고, 선택이 풀리면 사라진다.

**Rationale**: 모바일에서 길게 눌러 텍스트를 선택하면 브라우저가 **자체 복사·공유 메뉴를
선택 위에 띄운다**. 그 위치에 우리 버튼을 두면 가려지거나 겹친다(spec.md 엣지 케이스에
기록된 항목). 브라우저 기본 메뉴의 위치·크기는 통제할 수 없으므로 애초에 겹치지 않는
곳에 두는 것이 유일하게 안정적이다.

고정 영역은 `Range.getBoundingClientRect()` 계산이 필요 없어 코드도 단순하고, 키보드
사용자에게도 위치가 예측 가능하다.

**Alternatives considered**:
- 선택 위 떠 있는 말풍선 — 데스크톱에서는 깔끔하지만 위 이유로 모바일에서 무너진다.
  모바일 우선(원칙 III)이므로 모바일이 기준이다.
- 화면 하단 고정 바 — 겹침은 피하지만 스크립트와 멀어져 무엇에 대한 동작인지 흐려지고,
  하단 탭바(`.bottom-nav`, 78px)와 자리를 다툰다.

## R-007: FR-027 용어 정리 범위

**Decision**: 아래 식별자와 문구를 바꾼다. 구현 시 한 번에 처리하고 이후 새 코드는 새
이름만 쓴다.

| 현재 | 변경 후 | 위치 |
|---|---|---|
| `.word-card` | `.expression-card` | `globals.css`, `page.tsx` |
| `.word-index` | `.expression-index` | 같음 |
| `.jp-word` | `.expression-term` | 같음 |
| `.ko-word` | `.expression-meaning` | 같음 |
| `.flashcard` | `.flip-card` | 같음 (복습 화면의 뒤집는 카드) |
| `<h1>플래시카드</h1>` | `<h1>내 표현</h1>` | `page.tsx` `Cards` |
| "플래시카드 영구 저장" | "표현 영구 저장" (그리고 미구현 목록에서 제거) | `README.md` |

**Rationale**: Constitution v1.1.0 원칙 I이 "용어집의 '쓰지 않는 말'을 문서·코드 식별자·
화면 문구에 사용해서는 안 된다"(MUST NOT)로 규정했다. `word-*`는 용어집이 금지한 "단어"
이고, `flashcard`는 금지한 "플래시카드"다.

`.flashcard` → `.flip-card`로 간 이유는 `.expression-card`가 카드 목록의 항목에 이미
쓰이고, `.review-card`는 홈 화면의 복습 진입 카드가 이미 쓰고 있어서다. 복습 화면의 그
요소는 "뒤집는 카드"라는 형태를 가리키므로 `flip-card`가 정확하다.

**Alternatives considered**:
- 이름을 그대로 두고 문구만 바꾸기 — 원칙 I이 코드 식별자를 명시적으로 포함하므로 위반이
  남는다.
- 나중에 별도 기능으로 정리 — 이 기능이 그 화면들을 어차피 고쳐 쓰므로 지금이 가장 싸다.
  나중으로 미루면 새 코드가 낡은 이름 위에 쌓인다.

## 결론

미확정 항목이 남지 않았다. 신규 런타임 의존성은 0개이고, 원칙 III 게이트 실패는 R-002가
코드 한 줄로 해소한다. Phase 1 설계로 진행한다.
